# 维护成本与收益：首轮测量设计

## 2. 四种成本分开记录

1. **开发本 Skill 的成本**：设计、实现工具与页面、维护 Skill。本身是产品开发投入，不混入每个被维护项目的日常开销；完整投入分析可另行摊销。
2. **项目初次接入成本**：建立身份、绑定已有文档、整理当前目标和必要关系。计入有无 Skill 的主对照，历史补录按实际范围计入。
3. **持续开发成本**：加载指令、检索、读取材料、维护记录、正常实现、验证和返工。主要结论比较整个开发轨迹，不靠模型自行声称某段“属于维护”来精确归因。
4. **阅读与评估成本**：按需生成文字或图、真实用户阅读，以及实验中的模拟用户与评判模型。阅读是实际产品收益的一部分；评估器开销另列，不能算成开发智能体的维护开销，也不能从实验总费用中漏掉。

文件只读取一次，也可能在后续多个模型请求的上下文中继续出现。实际测量应累计宿主提供的请求/回合用量，核查字段是增量还是累计，避免重复求和。不要用文件读取次数代替 token 成本。

报告原始输入、输出、缓存命中和宿主可提供的缓存写入/推理明细。缓存与推理明细可能是输入或输出的子集，不再次加进总量。金额按实际模型和宿主的计费规则计算；缺少明细时明确不可用，不从账户总额度百分比推算该 Skill 的费用。[官方缓存文档](https://developers.openai.com/api/docs/guides/prompt-caching)

## 3. 值得先试的低成本设计

- **保留短入口，精确读取正文**：入口说明位置和边界；普通项目任务只读相关记录。检索先返回能判断的候选和位置，再打开必要正文；证据不足时扩大范围，不以节省 token 为由猜测。
- **初次接入先形成有用入口**：优先复用已有设计和需求，只补本次开发需要的空缺。额外历史整理明确为独立范围，避免把全部接入成本压在第一个小任务上。
- **在有长期变化时维护**：新要求先留下可定位的简短记录，实施明确后修订相关实现。修改、合并和剪枝均可；不在每次工具调用后写日志。保留需求、决定、实现和验证各自的含义，不追求最少文件数。
- **让读取结果可复用**：记录正文一处维护，来源与关系通过身份连接。重复检索和三种页面各写一份总结都应成为可诊断的额外开销。
- **阅读操作尽量由本地代码执行**：页面切换、展开、缩放与已建索引查询不逐次调用 LLM。需要新解释或图源适配时再计入生成成本。A/B/C 的可读说明来自共同记录，不能为零生成成本而退化为只展示机器字段。
- **机械整理在证明有用后脚本化**：例如 ID 定位、局部链接校验、渲染与索引更新。LLM 负责意图、解释和设计判断；不让模型反复生成相同机械脚本，也不为了未来可能使用而先搭大工具链。

这些是实施建议，不是每个任务必须执行的清单。不得新增强制审查、每轮全量建图、固定思考过程或逐条要求批准。OpenAI 的[技能与提示改进文章](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)支持短描述、条件读取与减少过度流程约束，但不能据此推断本 Skill 已经带来提升。

## 4. 正向提升需要发生在结果上

| 待验证的收益 | 可以观察的结果 | 不能冒充收益的现象 |
|---|---|---|
| 多轮需求保持 | 后期实现仍满足已经告知且未撤回的早期要求 | 文档中写着要求，但实现遗漏 |
| 更准确地理解改口 | 明确要求会更新，探索性想法仍保留未定状态 | 把每句询问都变成开发承诺 |
| 快速继续项目 | 新会话正确找到目标、理由和未完成项，用户少重复解释 | 摘要流畅但混淆当前与历史 |
| 改动少漏影响 | 找到真实接口消费者，并完成必要修改 | 列出更多无关依赖或全面扫描 |
| 开发者更容易理解 | 能找到条目，说明接口如何协作、为何这样设计 | 页面更漂亮或节点更多 |

关键风险是错误记录被反复引用，导致模型更坚持一个错误的“既定设计”。来源、提议/决定区分、当前状态与后继关系需要保留；代码观察与用户要求发生冲突时应解释差异，不能改写要求让代码显得正确。

## 5. 首轮对照建议

沿用[现有评估方案](../maintain-project-map/references/evaluation.md)中的隔离与用户模拟约定。先做一个约 6 个用户回合的试验，含新增需求、一次改口、一个小改动、换会话继续以及最终验收；目的先确认比较和计数可信，不从单次差异宣称提升。

主比较是相同条件的无 Skill / 有 Skill。无 Skill 组仍可正常记笔记。基线若本来就会维护良好文档，本 Skill 应显示额外价值，不能靠禁止基线记录来取得优势。

每条轨迹从初次接入累计到最终结果，列出：

- 验收结果与遗漏/回归，包括未完成和失败尝试。
- 整段轨迹的输入、输出、可用缓存明细、耗时和用户纠正；真人与模拟用户的纠正分列。
- 来源找回及换会话接续的准确性。
- 在小任务中的误触发、无关修改和不必要停顿。

同时回答两件事：相同预算内是否完成得更好；达到相同验收要求需要多少总成本。不能只统计成功样本来证明便宜。运行次数有限时报告每对结果和波动，不给没有依据的精确提升百分比。

先观察再设置日常开销目标；不预设一个适用于所有任务的硬 token 上限。若两组效果相当而开销增加，优先删减规则、缩小读取与维护范围。若结果更好但成本更高，由用户选择是否值得。若多轮累计成本尚未低于基线，则说明“在已测轮次内尚未回本”，不外推一个回本轮数。

用量和比较由运行日志及外部汇总收集，不要求正在开发的模型每轮填写成本报告。官方[Skill 评估指南](https://developers.openai.com/blog/eval-skills)支持捕获运行与产物、少量关键检查以及 token 用量；本项目的长期需求保持与阅读收益是额外的针对性设计。
