# 生命周期与剪枝

用于合并记录、收缩地图、退役功能或整理探索。资产应允许变小；保留可复用的经验和定位能力，不等于永久加载旧内容或保存所有执行日志。

## 1. 先辨明剪掉的是什么

| 操作 | 改变什么 | 仍需保留什么 |
|---|---|---|
| 阅读折叠 | 默认视图不展示低相关或历史内容 | 原条目、检索能力；不改变功能有效性 |
| 说明归档 | 核实说明已失效后将正文移入 archive/，原位置保留短定位 | 原始字节、ID、理由、证据、版本、替代说明或当前说明缺口；不改变功能或需求状态 |
| 记录合并/删冗余 | 合并重复说明，删除已被准确覆盖的正文 | 一个权威位置、旧 ID 到后继的定位及有意义的差异 |
| 功能/模块退役 | 根据需求变化淘汰、替换或合并原能力 | 原用途、退役依据、替代去向、版本与消费者处置状态 |
| 探索整理 | 收束尝试，移除过程噪声 | 有用的路线、结论、限制、证据和重新考虑条件 |

“从图里不显示”“不再需要这个功能”“已经删除实现”是不同事实。用户要求整理文档时，不据此扩展为删除代码；已经授权的功能移除不再增加一轮固定审批。

## 2. 功能退役与失败探索

**功能退役**回答“曾经提供什么，现在为何不再提供”。例如发布模块曾正常工作，后来因用户改为只做本地导出而退役。需求改变不说明实现曾经失败。

**失败探索**回答“为了什么尝试了什么，在什么条件下没有达到目标”。例如某种同步方法在试验中遗漏离线删除；记录触发条件、影响及证据，供后续开发避开同一问题。

“没选这个方案”“暂时不做”“没有做过试验”都不等于失败。某种方法在旧版本失败，也不代表所有环境永久不可行；依赖或目标变化时可以重新考虑。

探索成果可进入实现，已退役模块也可能包含值得复用的经验。通过来源或决策关系连接它们，保留不同语义。

## 3. 小范围执行，而非固定清理仪式

从用户当前要求或已存在的决定确定对象与范围。对相关对象核对：还有哪些有效需求依赖它、是否存在消费者、是否承载持久数据或旧版本兼容责任。核查深度由实际影响决定，不要求每次清理普查整个项目。

单次搜索没发现引用、最近没有改动、模型觉得复杂，只能产生候选，不能证明模块失效。意图未明确且影响产品行为时先提出具体方案；执行范围已有依据时继续完成。

如果目标是合并模块而保留能力，应维护功能到新实现的关系，不把功能也标为取消。如果模块只是退出未来设计但代码/调用还在，显示“待退役”及剩余事项；不能仅更新文档就声称实现已移除。

代码移除与消费者迁移按原任务完成对应检查，检查详情写入独立验证记录。访问不到的消费者保留待核对状态，不能把未知写成已经处理。

## 4. 当前视图可以剪短，历史仍可抵达

被移除的长记录可以通过 Git 查旧版。保留一个很短的定位条目即可，内容按实际需要包括：

- 原项目/记录 ID、原名称及常用别名。
- 已退役或已合并的状态、原因或决定来源。
- 替代条目（若有）、最后适用的版本或历史定位。
- 尚未解决的迁移/兼容问题（若有）。

定位条目可存于既有记录、清单或历史索引，不为每个删除动作另建长报告。尚未提交且有保留价值的内容，先留下必要摘录或归档，不能引用不存在的 Git 历史。

查询“现在怎么做”时默认给后继；查询旧名称或“以前那个怎么没了”时先展示退役原因和去向，可继续打开历史。当前视图可以默认隐藏退役项，历史搜索和直接 ID 定位仍覆盖它们。

确认失效的说明使用 `archive-record` 物理归档；变化但尚未核实只显示 needs_review。LLM 默认 search 排除归档正文，read 旧 ID 返回短定位；人读页面按同一边界展示，旧正文只在显式历史读取或独立归档页打开。外部绑定只归档本条记录的快照，不删除外部原文。命令、来源核对与归档字段见 [源码发现与说明归档](source-and-archive.md)。

不同分支可能保留同一模块的不同状态。关系在旧版本有效这一事实不随当前退役而消失；图按目标版本生成，不把历史依赖全局删除。

## 5. 失败探索保留到什么程度

只保存会改变未来判断的经验：问题、方案、结果、适用条件，以及支持结论的最少证据。完整工具日志、重复报错和随手尝试可不进入长期资产。

可沿用已有决策记录；只有探索量值得单独查询时才设 `records/explorations/`。失败的证据细节仍在验证/证据文件中，探索记录链接它并解释含义。

结果不明确时保留不确定性。把所有未采用路线叫作失败，会妨碍日后重新设计；删除所有失败路线，又会让模型反复走同一条已知有条件限制的路。
