# 组合项目、模块层级与扩展接口

仅在接入组合项目、调整模块层级、解释扩展接入或编写相关图源时阅读。普通单条需求修改不要求重新分析全部模块。

## 判断需要哪一层

先从现有需求、模块入口和合同确认职责，再选择文档层级。仓库、安装包、功能、模块与项目身份不是同一个概念。

- **建立子模块**：它有可独立解释的职责、对象归属、对外接口或维护边界，开发者需要单独查询或修改它。组合中的 Core、贴纸插件常满足这些条件；共享协议包可能只需一页说明。
- **继续拆子模块**：同一模块内部存在不同的扩展对象、消费者、协议/生命周期或变更影响，混写会让人误接接口或无法定位。例如“适配 Harness”和“适配业务插件”应分别维护，不能因都叫 Adapter 而合并。
- **停止拆分**：下一层只是函数、文件清单、私有实现细节，或拆开后不能独立解释职责。页面太长可以分章节，不必因此制造模块。不要按代码目录深度机械复制文档树，也不要预建一批空文件夹。
- **仍是一张项目地图**：子模块默认沿用项目 ID。已有独立维护地图的成员，链接其项目/条目 ID；组合页保留介绍和接入说明，不复制它的完整档案。

把选择落实在模块介绍和图中，说明本层职责、子模块及主要接口即可，不额外要求每次提交一份分类报告。证据缺失时标出未核实范围；不能为了少读材料而把已有不同职责压成一个黑箱，也不能编造内部模块来填满框图。

## 目录与权威资料

可采用下面的组织形状，名称和层级随真实项目调整：

```text
docs/project/
  project.yaml
  map.md
  records/
    modules/
      annotation-core/
        overview.md
        interfaces/
          references.md          # 提供方合同或既有合同的权威入口
          connected-plugins.md   # 已知接入者及接入说明链接
      sticker-board/
        overview.md
        integrations/
          annotation-core.md     # 消费方如何接入 + 合同链接
      maintenance/
        overview.md
        adapters/
          harness/
            overview.md
            contract.md
          business-plugins/
            overview.md
            contract.md
    verification/
  diagrams/
```

这不是必须一次生成的模板。若 Maintenance 本身就是当前项目，Adapter 可直接作为其子模块，不再套一层 maintenance。Harness 下只有确有独立维护需要时才分 Codex、DSH 等实现；业务 Adapter 同理。

records/ 内每个 Markdown 文件继续遵循[独立记录格式](asset-model.md)，不要把无元数据的目录说明放进去。实现可放所属模块下的独立 implementation 文件；验证另存，不能把测试日志塞进日常介绍。现有权威文档留在原仓库，由清单绑定精确标题/编号；目录入口可以链接这些章节，无需搬家或复制合同。

读取器递归发现 records/；B 侧栏按这些目录生成可展开层级，目录有 overview.md、index.md 或 README.md 记录时使用其标题。绑定的既有章节仍归在原资料入口，不为 UI 复制进模块目录。目录只承担阅读分组，不自动成为新项目或声明架构依赖。移动文件后检查相对链接和绑定，保持记录 ID。

## 提供方一份合同，双方各有接入说明

**合同唯一归提供方。** 它是 LLM 查实现约定的权威位置，也应让开发者理解：提供什么能力、由谁调用、输入输出、数据和写入归属、生命周期、错误/恢复、版本兼容及扩展边界。已有正式合同则直接引用/绑定，不能另抄一份完整定义。

**提供方的接入目录**列出已核实消费者：插件/模块、接入哪项接口、当前状态、已知适用版本和消费方接入文档链接。字段只填有依据的事实；源码已有依赖不证明当前实例已安装或启用。“已知接入者”不冒充全局完整清单。目录与合同可同页分节，条目多时再拆文件。

**消费方的接入文档**说明它接入哪个模块、用哪项接口完成自己的什么能力、涉及自身哪些功能，以及自身的适配约束和状态；链接回提供方合同与对应接入目录。不要重复提供方参数表、状态机或完整规格。

以“消费方的具体能力 → 实际使用的接口 → 作用与归属”为单位判断耦合，按需核对调用点或权威规格。一个入口使用某接口，不证明该模块的保存、删除、展示等其他操作也走同一接口；共用名称、安装依赖和服务注入也不证明全部能力发生直接调用。区分直接调用、间接依赖、计划接入和未核实范围，只有有依据的范围写为当前事实。记录足以定位依据即可，不要求逐函数清单或固定表格。这个判断同样适用于工作流步骤、Skill 工具调用和其他组合项目。

例如：Core 的“引用接口”旁有“已知接入者 → 贴纸”，点击进入贴纸的“接入 Annotation Core”；后者列出实际使用的 Core 能力，并提供返回 Core 合同的链接。双方展示是给开发者查关系的入口；LLM 默认读唯一合同与本次有关的接入说明，不必遍历所有消费者。

源码文档使用 Markdown 链接或明确记录 ID 的 Wiki 链接，记录同时保留提供/消费关系。`provides` 从提供模块指向合同，`consumes` 从消费模块或接入记录指向该合同；跨地图增加 project_id。每条语义关系只声明一次，读取器自动提供反向入口，不再同时写一份 `provided_by` / `used_by`。既有同义反向声明会合并显示并保留说明，不同角色、版本或机制不合并。正文链接只是阅读关联，不能据此自动推断调用、先后顺序或数据所有权。跳转规则见[阅读与交互](reading-and-interaction.md)。

**接入说明回答“接入谁、用什么、影响自己哪里”。** 不要求把它写成用户从开始到结束的经历，也不强制建立“跨模块功能”故事目录。仅在任务确实要解释执行顺序时另画/链接流程图；接口依赖本身不证明发生顺序。

## 两类 Adapter 不混写

以 Session Maintenance 为判断例子，具体字段仍查该项目权威合同：

| 文档分支 | 适配对象与职责 | 应定位的接入方 |
|---|---|---|
| Harness / 平台 Adapter | 宿主会话格式、身份、事件、版本、投影与运行证据等平台差异 | 相应 Harness/版本的适配实现 |
| 业务插件 / 扩展数据 Adapter | Annotation、贴纸、思维图等业务对象、所属会话、schema、写入方与领域操作 | 对应业务插件的接入说明 |

两者即使由同一 Engine 加载，也分别保存职责说明、合同入口和已知接入方。共用的身份/版本类型链接到同一权威定义；共享加载器可以引用两类接口，不将二者的权限或数据语义合成一个泛化 Adapter 合同。

## 用 Archify 表达实际结构

- **架构图**：按真实职责/归属使用 `boundaries` 包围本层相关内部功能，接口作为可识别节点或边端点；跨模块连线说明使用的能力。保留上层总览，必要时提供局部展开。已知接口和关键子模块不能仅因总图拥挤就消失；细节可链接到局部资料。私有函数不要求全部画出。
- **扩展能力**：明确谁提供接口、哪些已知模块接入，分别连接到相应接口/内部功能。两个 Adapter 家族分别表示；不能用同一个“Adapter”节点让人误以为可互换。依赖、状态通知和真正执行顺序分别标注。
- **流程图**：有明确执行证据时按负责组件设置 `lanes`，在需要的泳道内用 `groups` 框出该组件的相关步骤；各步应能定位其所属模块，跨泳道连线说明交接。异常分支保留具体负责方，不用“正常/异常”两个通用泳道抹掉所有权。无关组件不必出场。
- **层级与工具限制**：架构的 boundaries 包围组件 ID；工作流的 groups 受泳道和列范围约束，不是任意递归子图。深层结构超出原生表达时采用本层图加局部图/文档链接。当前 A/B 清单各接一份架构和流程图；额外图不能伪称已自动接入页面，需按工具实际能力登记/交付。

沿用[Archify 图源维护](archify-authoring.md)的原生 schema、节点绑定与校验。框表示真实边界，不能仅为装饰加框；不同接口也不能只靠颜色区分。

## 交付时检查是否讲清楚

只检查本次涉及的范围：开发者能否找到模块/子模块职责，区分不同扩展接口，从提供方到达相关接入说明并返回合同；图是否能指出相关内部功能和实际交接；是否只有一份完整合同。

若交付仍只有插件名称清单、双方各抄一份合同、没有负责方的长流程线，或把所有 Adapter 混为一类，应补足上述信息再称为完成。原生图校验通过只证明格式/布局检查，不证明这些语义已经表达，也不证明全部接入方已发现。
