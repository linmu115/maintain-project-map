# 开发历程如何改为按需取证

## 问题：已有来源又被复制了一遍

开发历程第一版已经能够解释任务并展开依据，但还在地图中保存原文副本和预先导出的片段。用户发现工具调用也进入日志，指出 Codex 本身已有会话记录，并同时担心磁盘占用和模型上下文。

[查看依据：用户提出重复存储与上下文顾虑](history-event:EVT-f9ccb323ce6b71bdd331)

## 判断：核查价值与保存方式分别处理

公开答复承认来源保存过多，保留关键证据的核查能力，把工具原文改为请求时从原会话读取。答复同时说明：当时并没有把全部日志自动注入模型，存储冗余与上下文读取是两个需要分别检查的问题。

[查看依据：接受修正后的实施方向](history-event:EVT-aa05735ed9997b9418ba)

## 调整：保存定位，展开时读取原文

实现保存事件身份、行号和内容指纹；读取选定内容时核对来源，工具调用和返回按调用身份配对。迁移结果显示，该实例的原文记录从 659263 字节变为 88702 字节的定位索引，移除了 329 个生成片段文件。数字仅描述这一次迁移。

[查看依据：实际迁移调用与返回](history-event:EVT-cde2749f67607564ed19)

## 验证：来源仍可回查，也要明确失效

测试补充了原会话消失、对应内容改变、片段续读以及导出不保存原文等情况；检查在临时材料上执行，没有删除真实用户会话。真实实例随后核对重复索引不变、索引中没有原文字段，以及页面事件目录仍只有一个。

[查看依据：读取与来源失效的检查改动](history-event:EVT-42e66b2198c17828886b)

## 结果与仍需保留的边界

本轮交付保留了过程叙述和按需证据，当前能力与完整检查范围分别由实现、验证记录维护。原会话若被移走或删除，整理正文仍可阅读，来源原文不能凭索引恢复。没有把“某次历史失败”转成以后禁止尝试的规则。
